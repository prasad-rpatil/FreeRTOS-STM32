STM32 NUCLEO + FreeRTOS PROJECT
CODE EXPLANATION, INITIALIZATION REQUIREMENTS AND LOGIC
========================================================

1. PROJECT OVERVIEW
-------------------
This project is an STM32 Nucleo-board FreeRTOS application using three tasks:

1. Handler Task  - High priority
2. Logger Task   - Low priority
3. Medium Task   - Normal priority

The project demonstrates:
- FreeRTOS task priorities
- Binary semaphore
- Mutex
- Interrupt-to-task synchronization
- UART resource protection
- Priority-related scheduling behavior
- Measuring how long a task waits to acquire a mutex
- A low-priority task deliberately holding a mutex
- A medium-priority task doing continuous CPU work

The main synchronization objects are:

    buttonSemaphore
    uartMutex

The button interrupt releases buttonSemaphore.
Handler_Task waits for that semaphore.
Logger_Task and Handler_Task both use uartMutex before transmitting through UART2.

4. SYSTEM CLOCK INITIALIZATION
------------------------------
SystemClock_Config() configures the MCU clock.

The code uses:

    HSI48 = 48 MHz internal oscillator

PLL is disabled.

The system clock source is:

    HSI48

Clock dividers:

    AHB  = SYSCLK / 1
    APB1 = HCLK / 1

USART2 uses PCLK1 as its clock source.

The clock must be initialized before normal peripheral operation.

6. UART2 INITIALIZATION
-----------------------

    Baud Rate     = 38400
    Word Length   = 8 bits

    Mode          = TX/RX

UART2 is the communication interface used to print the messages from

Because more than one task can use UART2, a mutex is required to

8. FREErtOS KERNEL INITIALIZATION
---------------------------------
After the HAL and peripherals are initialized, the scheduler is

    osKernelInitialize();

This initializes the RTOS kernel before creating the RTOS objects
and tasks.


9. SEMAPHORE INITIALIZATION
---------------------------
A binary semaphore is created:

    buttonSemaphore = xSemaphoreCreateBinary();

The code checks that creation succeeded:

    configASSERT(buttonSemaphore != NULL);

Purpose:
The semaphore transfers the button interrupt event from the ISR
(interrupt service routine) to Handler_Task.

Initial logic:

    Button pressed
          |
          v
    GPIO interrupt
          |
          v
    HAL_GPIO_EXTI_Callback()
          |
          v
    xSemaphoreGiveFromISR()
          |
          v
    buttonSemaphore
          |
          v
    Handler_Task wakes up


10. MUTEX INITIALIZATION
------------------------
A mutex is created:

    uartMutex = xSemaphoreCreateMutex();

The code checks:

    configASSERT(uartMutex != NULL);

Purpose:
The mutex protects UART2.

Both Handler_Task and Logger_Task need access to UART2. Only one
task should transmit at a time.

Basic logic:

    Handler_Task ----\
                      >---- uartMutex ----> UART2
    Logger_Task  ----/

If one task owns the mutex, the other task must wait until the mutex
is released.

12. TASK PRIORITY ORDER
-----------------------
The intended priority relationship is:

    HIGH
      |
      | Handler_Task
      |
    NORMAL
      |
      | Medium_Task
      |
    LOW
      |
      | Logger_Task

Therefore:

Handler_Task > Medium_Task > Logger_Task

In FreeRTOS, a ready higher-priority task normally gets CPU time before
a ready lower-priority task.


13. SCHEDULER START
-------------------
After the RTOS objects and tasks are created:

    osKernelStart();

The FreeRTOS scheduler starts.

After this point, execution is controlled by the RTOS scheduler.

The while(1) loop in main() should normally never be reached.


14. INTERRUPT LOGIC
-------------------
The button is connected to GPIOC pin 13.

The callback is:

    HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)

When PC13 generates the interrupt:

    if (GPIO_Pin == GPIO_PIN_13)

the code executes:

    xSemaphoreGiveFromISR(
        buttonSemaphore,
        &xHigherPriorityTaskWoken
    );

Then:

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);

Purpose of portYIELD_FROM_ISR():
If releasing the semaphore makes a higher-priority task ready, the
scheduler can immediately switch to that task after the ISR finishes.


15. HANDLER TASK LOGIC
----------------------
Handler_Task is the high-priority task.

The task first waits for the button semaphore:

    xSemaphoreTake(buttonSemaphore, portMAX_DELAY)

This means the Handler task sleeps/blocks until the button interrupt
occurs.

When the button event occurs:

    1. Handler_Task wakes up.
    2. waitStart stores the current FreeRTOS tick count.
    3. Handler_Task tries to acquire uartMutex.
    4. If Logger_Task owns the mutex, Handler_Task blocks.
    5. Once Handler_Task obtains the mutex, waitEnd is recorded.
    6. Mutex wait time is calculated.
    7. LED is toggled.
    8. UART messages are transmitted.
    9. uartMutex is released.
   10. Handler_Task goes back to waiting for the next button event.

The wait-time calculation is:

    waitTime = waitEnd - waitStart;


16. HANDLER TASK UART MESSAGE
-----------------------------
The Handler task prints:

    [HANDLER] Button event received
    [HANDLER] UART mutex acquired
    [HANDLER] Mutex wait = %lu ms

The purpose is to demonstrate how long the high-priority task had to
wait for the UART mutex.

IMPORTANT:
The variable is measured in FreeRTOS ticks. The printed label says
"ms". This assumes the FreeRTOS tick configuration corresponds to
milliseconds (commonly a 1 kHz tick). The exact conversion depends
on configTICK_RATE_HZ.


17. LOGGER TASK LOGIC
---------------------
Logger_Task has low priority.

At startup it first executes:

    vTaskDelay(pdMS_TO_TICKS(500));

So it waits for approximately 500 ms before beginning its main loop.

Inside the loop:

    1. Logger_Task tries to acquire uartMutex.
    2. Once it gets the mutex, it prints a message.
    3. It deliberately holds the mutex for approximately 5 seconds.
    4. It prints a release message.
    5. It releases uartMutex.
    6. It delays for approximately 2 seconds.
    7. The cycle repeats.


18. LOGGER TASK PURPOSE
-----------------------
The Logger task intentionally creates a long mutex-holding period.

This line:

    while ((xTaskGetTickCount() - startTime) <
           pdMS_TO_TICKS(5000))
    {
        __NOP();
    }

keeps the task active for about 5 seconds while it owns uartMutex.

This is designed to demonstrate what happens when a high-priority task
needs a resource currently owned by a lower-priority task.


19. MEDIUM TASK LOGIC
--------------------
Medium_Task has normal priority.

At startup:

    vTaskDelay(pdMS_TO_TICKS(1000));

It waits approximately 1 second.

Then it continuously increments:

    counter++;

The task does not block inside its infinite loop.

Its purpose is to create continuous CPU activity at a priority between
Handler_Task and Logger_Task.

21. IMPORTANT SYNCHRONIZATION LOGIC
------------------------------------
There are TWO different synchronization mechanisms.

A. Binary Semaphore
-------------------
Object:

    buttonSemaphore

Used for:

    ISR -> Handler_Task notification

It does NOT protect UART.

It tells Handler_Task:

    "A button event has happened."

B. Mutex
---------
Object:

    uartMutex

Used for:

    Protecting UART2

It ensures:

    Handler_Task and Logger_Task do not access UART2 simultaneously.

23. PRIORITY INVERSION / INHERITANCE CONTEXT
--------------------------------------------
This project is useful for demonstrating priority-related mutex
behavior.

The priorities are:

    Handler_Task = HIGH
    Medium_Task  = NORMAL
    Logger_Task  = LOW

Logger_Task can hold uartMutex while Handler_Task needs it.

A FreeRTOS mutex normally supports priority inheritance. Therefore,
when a higher-priority task is blocked waiting for a mutex held by a
lower-priority task, the mutex owner's priority can be temporarily
raised to reduce priority inversion.

The exact scheduling behavior depends on the FreeRTOS configuration
and the timing of the tasks.

26. IMPORTANT FUNCTION DIFFERENCES
----------------------------------
xSemaphoreTake()
    Used from task context to obtain a semaphore/mutex.

xSemaphoreGive()
    Used from task context to release a semaphore/mutex.

xSemaphoreGiveFromISR()
    Used inside an interrupt service routine.

vTaskDelay()
    Blocks the current task for a specified number of ticks.

xTaskGetTickCount()
    Returns the current FreeRTOS tick count.

pdMS_TO_TICKS()
    Converts milliseconds to FreeRTOS ticks.

portYIELD_FROM_ISR()
    Requests a context switch after an ISR when appropriate.


27. WHY THE ISR SHOULD NOT USE NORMAL TASK APIs
-----------------------------------------------
The button interrupt executes in interrupt context.

Therefore the code correctly uses:

    xSemaphoreGiveFromISR()

instead of the normal:

    xSemaphoreGive()

The FromISR API is designed for interrupt context.


28. WHY A MUTEX IS USED FOR UART
--------------------------------
UART is a shared resource.

Both:

    Handler_Task
    Logger_Task

can transmit using:

    HAL_UART_Transmit()

Without a mutex, two tasks could attempt to use the UART at the same
time, which could result in mixed or corrupted output.

The mutex provides exclusive ownership.

Pattern:

    Take mutex
        |
        v
    Use UART
        |
        v
    Give mutex


29. WHY A BINARY SEMAPHORE IS USED FOR THE BUTTON
-------------------------------------------------
The button event is generated asynchronously by hardware.

The ISR should remain short.

Instead of performing the complete button-processing operation inside
the ISR, it signals Handler_Task.

This provides:

    ISR
      |
      | quick notification
      v
    Handler_Task
      |
      | normal task execution
      v
    UART + LED + processing


30. TASK STATES IN THIS PROJECT
-------------------------------
Handler_Task:
    Usually BLOCKED waiting for buttonSemaphore.
    It becomes READY when the button interrupt releases the semaphore.
    It may become BLOCKED again waiting for uartMutex.

Logger_Task:
    Delays initially.
    Attempts to acquire uartMutex.
    Holds the mutex for approximately 5 seconds.
    Delays approximately 2 seconds after releasing it.

Medium_Task:
    Delays initially.
    Then continuously executes its counter loop.

The RTOS scheduler determines which READY task executes.

33. IMPORTANT OBSERVATIONS FROM THE PROVIDED CODE
--------------------------------------------------
The source code contains declarations named:

    Handler_TaskHandle
    Logger_TaskHandle
    Medium_TaskHandle

and Cube-generated thread attributes.

However, the actual task functions shown later are named:

    Handler_Task()
    Logger_Task()
    Medium_Task()

The task creation calls shown in the provided source use:

    osThreadNew(HandlerTask, ...)
    osThreadNew(LoggerTask, ...)
    osThreadNew(MediumTask, ...)

while the function definitions shown later use underscores:

    Handler_Task()
    Logger_Task()
    Medium_Task()

These names must match in the actual compilable project. If the source
really contains this mismatch, it should be corrected to the actual
function names used by the project.

Also, TIM2 is initialized but is not used by the task logic shown.
The mutex wait measurement is based on xTaskGetTickCount().


34. SIMPLE EXPLANATION FOR PRESENTATION / VIVA
----------------------------------------------
If asked "What is your project doing?", explain:

"This STM32 Nucleo project demonstrates FreeRTOS task scheduling and
synchronization. I have created three tasks with high, medium and low
priorities. A button interrupt generates an event and gives a binary
semaphore to the high-priority Handler task. The Handler task then
tries to access UART2 through a mutex. A low-priority Logger task also
uses the same UART mutex and intentionally holds it for about five
seconds. This allows us to observe mutex blocking and task scheduling.
A normal-priority Medium task continuously runs in the background.
The Handler task measures the time it waits for the UART mutex, toggles
the LED, and prints the result through UART."

37. FINAL SUMMARY
-----------------
The core idea of the project is:

    Hardware interrupt
          |
          v
    Binary semaphore
          |
          v
    High-priority Handler Task
          |
          v
    UART mutex
          |
          +-----------------------------+
          |                             |
          | UART available              | UART owned by Logger

       Transmit                     Handler blocks
          |                             |
          +-------------+---------------+

The Logger task intentionally holds the UART mutex for a long time,

synchronization behavior.
